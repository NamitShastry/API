AeroIndex Feature Register: Tier 2 (F041–F090) 
Tier 2 is the core engine and core dashboards: route basket, collection, cleaning, 
the index maths, the main dashboards and live updates. Same format as Tier 1: What it 
is / How it works / Data & API / Edge cases / Done when. 
Scale figures used below. The locked basket is 20 directional routes × 7 lead buckets 
× 8 sources = 1,120 searches per cycle, about 30 offers each, so roughly 33,600 
quotes per cycle and about 134,000 per day at four cycles. (This corrects the larger 
40-route figures used earlier for sizing. Both fit comfortably in the design.) 
New tables introduced in this tier (add to 
migrations): product, base_price, chain_link, sim_route_params, event_calenda
r, tax_rule, fare_family_map, cell_stats, sim_truth. Their definitions are given 
under the features that need them and collected at the end. 
 
A. Collection 
F041 — Route basket registry 
What it is. The authoritative list of routes the index measures, with their weights, 
versioned over time. 
How it works. 
• 
Tables: ref_route (all known routes), basket_version (a named, dated 
basket), route_weight (route weights inside a basket). One basket is active at a 
time. 
• 
Locked basket (20 directional routes): DEL-BOM, BOM-DEL, DEL-BLR, 
BLR-DEL, DEL-HYD, HYD-DEL, DEL-CCU, CCU-DEL, DEL-MAA, MAA-DEL, 
BOM-BLR, BLR-BOM, BOM-HYD, HYD-BOM, BOM-GOI, GOI-BOM, BLR-
HYD, HYD-BLR, plus DEL-GOI and GOI-DEL if you want 22 (the seed script 
accepts any list in the CSV). 
• 
Selection rule (documented in the methodology): rank city pairs by 
DGCA passenger traffic, take the top N covering at least a stated share of 
domestic traffic, and require that at least 3 sources sell the route. The rule and 
the source document are stored on basket_version.weight_source. 
• 
Each route belongs to attributes used for sub-
indices: is_metro_pair, route_group (METRO_METRO, METRO_TIER2, TIER2_TI
ER2), distance_band. 
• 
A database trigger enforces that weights per basket sum to 1 (±1e-6) before a 
basket can be activated. 
• 
Activation is effective-dated (effective_from at a month boundary) so 
history is never re-weighted silently (see F073). 
Data / API. GET /api/v1/routes, GET /api/v1/basket/{id}, POST 
/api/v1/basket (F096). 
Edge cases. Removing a route mid-year is a methodology change requiring approval 
and chain-linking. A route with no data for 7 days is flagged DORMANT and surfaced to 
Data Health but stays in the basket until formally removed. 
Done when. Seeding produces a valid active basket, the sum-to-one trigger rejects a 
bad basket, and route attributes drive the group sub-indices. 
F042 — Lead-time window planner 
What it is. Defines how far ahead of departure each fare is observed, and turns "L07" 
into an actual departure date to search. 
How it works. 
• 
Buckets (locked): L01, L03, L07, L15, L30, L45, L60, with target days 1, 3, 
7, 15, 30, 45, 60. The problem statement's windows (1, 7, 15, 30, 45) are all 
included. 
• 
Bucket assignment ranges for observed lead days (used when a data source 
supplies a lead that isn't exact): L01 1–2, L03 3–5, L07 6–10, L15 11–21, L30 22–
37, L45 38–52, L60 53–70. 
• 
The planner sets departure_date = obs_date + target_days (IST calendar 
date). 
• 
Lead days are computed from IST dates, never from timestamps, to avoid off-by-
one errors at midnight. 
• 
Buckets can be added later (for example L90 for international) without code 
changes, because weights live in lead_weight. 
Edge cases. If a source's booking horizon is shorter than a bucket (a carrier that 
doesn't sell 60 days ahead), tasks for that pair are marked SKIPPED with 
reason BEYOND_HORIZON, and the cell relies on other sources. 
Done when. Unit tests confirm the date arithmetic across month ends, leap days and 
IST midnight, and that every observed lead maps to exactly one bucket. 
F043 — Source registry and adapter contract 
What it is. The list of places fares come from, and the one interface every source 
implements. 
How it works. 
• 
ref_source rows: INDIGO_DIRECT, AIRINDIA_DIRECT, AKASA_DIRECT, SPICEJE
T_DIRECT, MMT, YATRA, CLEARTRIP, GOIBIBO, plus SIMULATOR, REPLAY, and 
reserved LICENSED_* codes. 
• 
Each source has: channel (AIRLINE_DIRECT, OTA, LICENSED_FEED, SIMULATOR), 
delay bounds (defaults 2000–5000 ms), daily request cap, enabled 
flag, adapter_version, and a terms_reviewed record (who, when, outcome) 
that gates live scraping (F049). 
• 
Adapters are discovered through a registry (entry points), so adding a source 
means adding a module and one database row. 
• 
The contract (the FareSourceAdapter protocol) 
has fetch(task) returning RawOffer items and healthcheck(). 
• 
Every adapter ships with contract tests: recorded payloads 
in tests/golden/{source}/ that must parse to expected RawOffer lists. 
Data / API. GET /api/v1/sources (with health), POST 
/api/v1/ops/sources/{code}/pause|resume. 
Edge cases. A disabled source is skipped by the planner and excluded from the 
coverage denominator, with the change recorded in the audit log. 
Done when. Swapping the simulator for a different adapter requires no change outside 
the adapter package, and every enabled adapter passes its golden-payload tests. 
F044 — Sampling plan and task generator 
What it is. Turns the basket and lead windows into the concrete list of searches to run 
each cycle. 
How it works. 
1. For each enabled source that sells the route, for each route in the active basket, 
for each lead bucket: create one SearchTask (route × bucket × source). 
2. Idempotency key: cycle_id|source|route|bucket. Re-running a planner for 
the same cycle creates no duplicates. 
3. Ordering: higher-weight routes first, then a random shuffle inside each priority 
band, so a cycle cut short still covers the most important cells. 
4. Pacing: per-source token buckets enforce delays and daily caps (F050). 
5. Tasks are written to scrape_task (status QUEUED) and pushed onto the queue. 
6. Planned count per cycle is stored on scrape_cycle.planned_tasks, which 
becomes the denominator for coverage (F069). 
Data / API. Tables scrape_cycle, scrape_task. Redis Stream scrape.tasks. 
Edge cases. If a route is sold by only one source, tasks for that pair are 
marked single_source so the coverage report can flag fragility. 
Done when. A planner run for the seeded basket creates exactly 1,120 tasks (minus any 
source-route pairs not sold), and a second run for the same cycle creates zero. 
F045 — Collection scheduler (cycles) 
What it is. The clock that starts collection cycles reliably. 
How it works. 
• 
APScheduler runs in the collector container with a persistent job store. Default 
cycles at 00:30, 06:30, 12:30, 18:30 IST, each staggered per source by a 
random offset of 0 to 10 minutes. 
• 
Leader lock: only one collector instance schedules, using a Redis lock with a 60 
s lease renewed every 20 s. 
• 
Cycle state machine: PLANNED → RUNNING → COMPLETE | PARTIAL | 
FAILED. PARTIAL means at least 70% of tasks resolved before the deadline 
(default cycle deadline 3 hours). 
• 
Misfire grace: a cycle missed by up to 15 minutes still starts. Beyond that it is 
skipped and an alert fires. 
• 
No overlapping cycles: a new cycle does not start if the previous one is still 
running (it is logged as SKIPPED_OVERLAP). 
• 
Manual controls (role DATA_OPS): trigger an ad-hoc cycle, pause and resume all 
collection. Every action is audited. 
• 
Emits progress events every 10 s to ops.cycle for the Data Health page. 
Edge cases. After a restart, in-flight tasks whose visibility timeout expired are re-
queued (F053). Clock changes are irrelevant because all schedules use IST timestamps 
with explicit timezone. 
Done when. Killing the collector mid-cycle and restarting it resumes without 
duplicating tasks, and the overlap and misfire rules behave as specified in tests using a 
fake clock. 
F046 — Calibrated simulator 
What it is. The richer, realistic version of the basic simulator (F039), tuned to 
published anchors, and the source of every demo number. 
How it works. Extends F039 with: 
• 
Per-route parameters in sim_route_params(route_id, base_fare, tau, 
lead_amp, dow_profile, season_profile, volatility), loaded from a 
calibration file rather than hard-coded. 
• 
Calibration procedure: (1) set each route's base_fare so the simulated 
monthly average lands at the published DGCA level where available, (2) 
fit tau from any real fare samples you collected by hand, (3) record the sources 
in docs/simulator_calibration.md. Uncalibrated parameters are marked 
"illustrative" in the methodology page. 
• 
Carrier structure: CarrierFactor distinguishes LCC (about 0.92 to 1.00) 
from FSC (about 1.10 to 1.30), and carriers move together via a common route 
shock plus a smaller carrier-specific shock (total = 0.7·common + 
0.3·specific), which makes cross-carrier agreement (F123) meaningful. 
• 
Seat dynamics: seats_left starts high and falls as lead shrinks; probability 
of SOLD_OUT rises for lead ≤ 3 and on peak days. 
• 
Fare-family ladder: Saver, Standard/Flexi, Corporate with price multipliers 
(1.00, 1.12–1.25, 1.35–1.60). The index uses the lowest available Saver-
equivalent family by default (configurable). 
• 
Channel effects: OTAs add convenience fees and occasionally show a small 
discount on the same flight. 
• 
Events: the festival calendar (F047) adds demand bumps; a "fuel surcharge 
step" scenario raises fuel_surcharge by a fixed share from a given date. 
• 
Determinism: one seed drives everything; a scenario file can script events 
("inject +18% spike on DEL-BLR L07 from 09:40"). 
Done when. A generated month shows: lead-time ratio near 2.5, weekday pattern, 
festival bump at the right date, correlated carrier moves, and seat and sold-out 
behaviour per lead bucket, all asserted by statistical tests. 
F047 — Festival and event calendar 
What it is. A table of dated events that affect demand, used across simulation, charts, 
anomaly explanation and forecasting. 
How it works. 
• 
event_calendar(event_id, name, category, start_date, end_date, 
amplitude, width_days, direction, source_note, created_by). 
• 
Categories: FESTIVAL, HOLIDAY, LONG_WEEKEND, SCHOOL_VACATION, SPORTING, R
EGULATORY, FUEL_PRICE. 
• 
direction allows asymmetry: outbound travel rises before a festival, return 
travel after (OUTBOUND, RETURN, BOTH). 
• 
Dates are entered from official calendars by an admin (never inferred by the 
software) and each row carries a source_note, since festival dates vary by year 
and region. 
• 
Consumers: simulator demand bumps (F046), chart markers (F022), anomaly 
explanations ("window overlaps Diwali", F124), forecast regressors (F136). 
• 
CRUD in Admin, plus CSV import with validation. 
Done when. Events appear on charts, the simulator raises fares around them, and the 
anomaly explanation names them. 
F048 — Defect injector with ground-truth labels 
What it is. Deliberately adds realistic errors to simulated data, so the cleaning pipeline 
can be measured objectively. 
How it works. 
• 
Defect types and default rates: duplicates 1.5%, sold-out 1.0%, price parse 
errors 0.5% (dropped digit, 1,899 read as 1, currency symbol 
embedded), extreme outliers 0.3% (×8 or ÷8), missing components 
2.0% (only total shown), stale offers 0.1% (departure in the past), plus 
scenario-level defects: source outage (a source returns nothing for a window) 
and schema drift (a field renamed in one source). 
• 
Each injected defect is recorded as ground truth in sim_truth(raw_key, 
defect_type, injected_at). The truth field is stripped from the 
event before it enters the pipeline, so the cleaner can never read it. 
• 
After a run, the harness make dq-eval joins pipeline decisions to ground truth 
and reports precision and recall per defect type (for example "extreme 
outliers: recall 0.98, precision 0.95"). 
• 
Rates and seed are configurable, and deterministic. 
Done when. The evaluation report is generated automatically in CI and fails the build 
if recall on extreme outliers or duplicates drops below 0.9. 
F049 — Live Playwright adapter (one source) 
What it is. A real scraper for one search page, proving the adapter contract works on 
the actual web. Stretch goal: never allowed to block the demo. 
How it works. 
1. Gate: it refuses to run unless LIVE_SCRAPE_ENABLED=true and the source row 
has a terms_reviewed record (reviewer, date, outcome PERMITTED). 
2. Launches Chromium headless in an isolated container with resource limits (1 GB, 
2 CPUs, 60 s hard timeout per search). 
3. Applies polite crawling (F050), then opens the search page, fills origin, 
destination and date (or uses a deep link with query parameters), and waits for 
results. 
4. Primary extraction: a page.on("response") handler captures the JSON 
response the page itself consumes. Fallback: DOM extraction with resilient 
selectors (data-testid/ARIA first, text patterns second). 
5. Saves the raw payload (F052), parses 
to RawOffer (data_origin='LIVE_SCRAPE'), publishes to the bus. 
6. Volume cap: at most 20 searches per day per source in H, spaced by the delay 
window. 
7. On block, CAPTCHA, timeout or parse failure: takes a screenshot, records the 
error code, marks the task BLOCKED or FAILED, and does not attempt to 
circumvent anything. 
Edge cases. If any check fails, the system falls back to the simulator for that cell, and 
the UI shows the origin mix honestly (F014). 
Done when. One real page yields correctly parsed offers on at least a test run, a forced 
failure produces a clean fallback, and the gate blocks execution when the terms record is 
missing. 
F050 — Polite crawling 
What it is. The rules that keep collection respectful, compliant and low-impact. 
How it works. 
• 
robots.txt: fetched per host and cached 24 hours, evaluated with 
Python's urllib.robotparser. Disallowed paths are never requested. A Crawl-
delay directive overrides the default delay if longer. 
• 
Identity: the user agent is CPI-IndexBot/1.0 (+https://<your-
domain>/bot), with a public page describing the bot's purpose and a contact 
address. 
• 
Rate: one request in flight per host, a random 2–5 s delay between actions, a 
per-host daily cap, and off-peak scheduling by default. 
• 
Back-off: on HTTP 429 or 503, honour Retry-After; otherwise exponential 
back-off. Three consecutive blocks in a cycle open the source's circuit breaker 
(F118). 
• 
Never: solve CAPTCHAs, spoof identities to evade blocks, use credentials or log 
in, create bookings or add items to a cart. 
• 
Kill switch: a single setting SCRAPING_ENABLED=false stops all live collection 
immediately. 
Done when. A test proxy server verifies that disallowed paths are never requested, that 
delays fall in the configured range, and that a 429 leads to back-off. 
F051 — Proxy and fingerprint manager (production) 
What it is. Manages the network identities collectors use, to spread load and keep 
collection stable. Designed now, built in production. In H, collectors use one direct 
egress route. 
How it works (P). A pool of provider-supplied proxies (India-region), each with a 
health score (success rate, latency, ban signals) stored in Redis (proxy:health:{id}). 
A worker leases a proxy plus a coherent browser profile (user agent, viewport, 
locale en-IN, timezone Asia/Kolkata) and holds it for a session so cookies stay 
consistent. Unhealthy proxies are retired for a cool-down. Credentials are encrypted at 
rest with per-tenant keys. Cost per request is tracked. Ethics: rotation exists to spread 
load, not to defeat access restrictions, and the rules in F050 still apply. 
Done when (P). Lease, release and health scoring pass tests against a mock provider. 
F052 — Raw capture store with content hashes 
What it is. A permanent, tamper-evident copy of exactly what each source returned. 
How it works. 
• 
Each response body is stored as a compressed file (zstd) under a content-
addressed path: raw/ab/cd/<sha256>.json.zst. 
• 
Sensitive headers and cookies are stripped before storage; only the body plus safe 
metadata (URL path without query secrets, status, timestamp) are kept. 
• 
A raw_capture row links the capture to its task (s3_uri, sha256, size). 
• 
Identical payloads are stored once. Maximum size 5 MB. An integrity job re-
hashes a random 1% sample nightly. 
• 
Retention: keep indefinitely (compressed size is small). In production the bucket 
uses write-once object lock. 
• 
The Provenance Drawer (F091) and Quote Inspector (F093) link quotes to 
their captures by hash. 
Edge cases. Simulated data has no capture; payload_sha256 is null and the inspector 
says "generated by simulator". 
Done when. Modifying a stored file makes the integrity job fail loudly. 
F053 — Task retry, backoff and skip handling 
What it is. Automatic, bounded recovery from failed searches. 
How it works. 
• 
Task states: QUEUED → RUNNING → SUCCEEDED | FAILED | BLOCKED | 
SKIPPED. 
• 
Error 
taxonomy: TIMEOUT, NETWORK, HTTP_4XX, HTTP_5XX, BLOCKED, CAPTCHA, PARSE, 
EMPTY_RESULT, BEYOND_HORIZON, POLICY (robots). 
• 
Retries for TIMEOUT, NETWORK, HTTP_5XX: up to 3 attempts with delays of about 
30 s, 2 min and 10 min, each with ±25% 
jitter. BLOCKED and CAPTCHA are not retried immediately; they count toward the 
circuit breaker. PARSE failures are quarantined with the capture kept for replay 
after a parser fix. 
• 
Visibility timeout: a running task not heartbeating for 5 minutes returns 
to QUEUED. 
• 
Poison tasks: after final failure the task is FAILED; a repeated failure pattern on 
the same cell triggers a notification. 
• 
Fallback: if a cell fails at one source, the planner does not silently substitute; 
coverage simply drops, unless the fallback ladder (F143) is enabled. 
Done when. Fault-injection tests confirm retry timing, jitter bounds, no duplicate 
results after a retry, and correct final states. 
 
B. Cleaning and Data Quality 
F054 — Parser and normaliser 
What it is. Converts whatever a source returned into one clean, standard structure. 
How it works. 
1. Decode and validate against the RawOffer schema. Anything unparseable 
becomes a rejected item with code R01. 
2. Price text parsing: handles ₹ 4,180, INR 4180.00, Rs. 4,180/-, Indian 
grouping (1,23,456) and stray spaces, converting to exact decimals (never 
floats). Ambiguous strings go to quarantine. 
3. Time handling: all timestamps parsed with their offsets, stored in 
UTC; obs_date derived in IST; flight_date is the local departure date. 
4. Identifier normalisation: flight numbers standardised (6E 
2041 becomes 6E2041), carrier names mapped to IATA codes via a mapping 
table, airport codes validated against ref_airport. 
5. Fare family mapping through fare_family_map(source_code, 
raw_label, normalised_family, tier) so "Saver", "SME", "Economy Lite" 
resolve to a common ladder. 
6. Derived fields: dow (of departure), dep_time_band (EARLY 00–
06, MORNING 06–12, MIDDAY 12–16, EVENING 16–21, NIGHT 21–
24), lead_days, lead_bucket, product_key. 
7. Output: a CleanCandidate passed to the rule engine. 
Done when. A golden test suite of at least 60 messy strings and payloads per adapter 
parses to the expected values. 
F055 — Deduplication engine 
What it is. Prevents the same fare from being counted twice. 
How it works. 
• 
dedup_hash = sha256(source | carrier | flight_number | 
departure_ts | cabin | fare_family | floor(scraped_at to 15 
minutes)). 
• 
First look-up in Redis (dd:{hash}, TTL 1 hour) for speed, then the database 
unique constraint (dedup_hash, scraped_at) as the final guard. 
• 
Same hash, same price: silent duplicate, counted in a duplicate metric and 
dropped. 
• 
Same hash, different price: the first is kept, the second is recorded 
as CONFLICTING_DUPLICATE in dq_issue for review, because it may signal a 
mid-window price change or a parsing bug. 
• 
Cross-channel duplicates (same flight via airline and OTA) are not dropped 
here; they are handled by the channel policy (F062). 
Done when. Replaying the same batch twice adds zero rows, and conflicting duplicates 
are logged. 
F056 — Sold-out and unavailable handling 
What it is. Correctly treats flights that can't be bought. 
How it works. 
• 
Availability values: AVAILABLE, SOLD_OUT, UNKNOWN. seats_left = 
0 implies SOLD_OUT. 
• 
Sold-out offers are excluded from price averages (the problem statement 
says to skip them) but are counted in a per-cell sell-out rate, a useful indicator 
on its own shown in the Route drill-down. 
• 
UNKNOWN availability with a valid price is kept and 
flagged AVAILABILITY_UNKNOWN. 
• 
LOW_SEATS flag when seats_left ≤ 3; the fare is retained, since scarcity pricing 
is real inflation. 
Done when. Sold-out offers never enter fare_quote_clean.is_index_eligible, 
and the sell-out rate is available via API.

F058 — Robust outlier detection (MAD) 
What it is. Statistical detection of implausible prices that is not fooled by the outliers 
themselves. 
How it works. 
• 
Score: z = |x − median| / (1.4826 × MAD) computed against a trailing 14-
day window of the same cell (route × lead bucket × departure weekday), read 
from cell_stats(cell_key, median, mad, n, updated_at) refreshed every 
15 minutes. 
• 
Thresholds: z > 5 flags, z > 7 rejects (configurable). 
• 
Cold start: with fewer than 30 observations, fall back to the route-level window 
with a wider threshold (reject at z > 9); with fewer than 10, only the absolute 
limits in R04 apply. 
• 
Excluded from the window: rejected quotes, so a run of bad data can't poison 
the baseline. 
• 
Market-move protection: if three or more carriers on the same route and 
bucket exceed z > 5 in the same direction within 2 hours, they are treated as a 
genuine market move: rejects are downgraded to flags with MARKET_MOVE, and 
the event is sent to the anomaly engine (F123). This prevents the cleaner from 
erasing real inflation, which is the exact problem the statement warns about. 
• 
The score is stored as outlier_score on the clean row for audit. 
Done when. On simulated data with injected outliers, recall exceeds 0.95 and false 
rejects during an injected festival spike are near zero (tested). 
F059 — Missing-data handling and imputation limits 
What it is. A transparent policy for gaps, never silently filling with zeros or guesses. 
How it works. 
• 
Cell missing (no valid observations that day): carry forward the previous 
day's cell relative for up to 2 consecutive days, flagged IMPUTED_CARRY. 
Beyond that, the cell is excluded and route weights renormalised (F066, F068). 
• 
Product missing today: simply not in today's matched set. It doesn't drag the 
average. 
• 
Component missing: stored as total-only (R11); excluded from component 
sub-indices but included in the total index. 
• 
Never impute price levels, only relatives, and never for more than two 
days. 
• 
Imputation rate (imputed cells ÷ all cells) is a published quality metric on the 
Data Health page, and appears in the coverage tooltip. 
Done when. Gap scenarios in tests produce the specified carry-forward, exclusion and 
renormalisation behaviour, and the imputation rate is reported. 
F060 — Quarantine store and review queue 
What it is. A holding area for questionable data, with human review. 
How it works. 
• 
Rejected and flagged items are written to dq_issue (rule, detail JSON, payload 
pointer) and streamed on fares.quarantine. 
• 
The Quality review tab (F117) lists issues with the quote, the rule, and a context 
chart of the cell's trailing distribution. 
• 
Actions for DATA_STEWARD: Accept (release into the clean 
ledger), Reject (confirm), Bulk accept similar (all issues of the same rule and 
cell in the window), Add rule exception. Every action requires a written 
reason. 
• 
Accepting reprocesses the quote through the pipeline with that rule bypassed, 
marks the day for recomputation, and creates a revision (F094) if the day is 
already OFFICIAL. 
• 
Queue SLA indicator: issues older than 48 hours are highlighted. 
• 
Auto-resolution: rejected duplicates and known-benign patterns resolve 
automatically as AUTO_REJECTED. 
Done when. Accepting a quarantined quote changes the affected day's value, and the 
change is auditable. 
F061 — Fare decomposition (base, fuel, taxes, fees) 
What it is. Splits every price into its parts, following CPI practice of tracking base price 
separately from taxes. 
How it works. 
• 
Components: base_fare, fuel_surcharge, taxes (government and airport 
levies, GST), convenience_fee (OTA-added, optional), and ancillaries (never 
included). 
• 
Index basis: total_fare = base + fuel + taxes. The convenience fee 
is excluded from the headline index because it is channel-specific and optional; 
it is tracked separately. 
• 
Identity check (R03): total ≈ base + fuel + taxes (+ fee) within ₹1. 
• 
Deriving missing parts: when only total is shown, tax parts are estimated 
using tax_rule(rule_id, component, rate_or_amount, applies_to, 
valid_from, valid_to, source_note), a configurable, effective-
dated table (never hard-coded, because tax rates and airport charges change; 
verify current values before use). Estimated splits are 
flagged ESTIMATED_SPLIT and excluded from component sub-indices. 
• 
Component sub-indices (F075) let analysts see whether an APIx move came from 
airline pricing, fuel pass-through or taxes. 
Done when. Tests confirm the identity, that convenience fees never enter the headline, 
and that estimated splits are labelled. 
F062 — Channel policy 
What it is. Prevents double counting of a flight seen through both an airline site and a 
travel platform. 
How it works. 
• 
Match across channels on flight_number + departure_ts + cabin + 
fare_family. 
• 
DIRECT_FIRST (default): if the airline-direct quote exists, use it in the index; 
keep the OTA quote as a spread sample (ota_total − direct_total). If only 
an OTA quote exists, use it and flag OTA_ONLY. 
• 
POOLED: use the mean of all channel quotes for the matched flight. 
• 
The policy and its rationale are stored in methodology_version.params and 
displayed on the Methodology page. Changing it is a methodology change 
needing approval. 
• 
Feeds the Channel comparison dashboard (F083). 
Done when. With both channels present, exactly one quote per flight enters the index 
under DIRECT_FIRST, and the spread sample is stored. 
 
C. Index Engine 
F063 — Product matching ladder 
What it is. Defines what counts as "the same item" across days, the foundation of a fair 
price index. 
How it works. 
• 
Ladder: (a) exact 
key carrier|flight_number|cabin|fare_family|lead_bucket; (b) fallback 
key carrier|dep_time_band|stops|fare_family|lead_bucket when no 
flight number is available; (c) otherwise stored but not index-eligible. 
• 
A product table (product_key, level, first_seen, last_seen, active, 
route_id) tracks lifecycle. A product unseen for 28 days becomes inactive. 
• 
Keys use normalised values (F054), so cosmetic differences don't create new 
products. 
• 
Fallback-key products are flagged MATCH_FALLBACK and their share per cell is 
reported. 
Edge cases. Flight-number changes on schedule seasons produce a new product, 
entering via overlap splicing (F074) so the index doesn't jump. 
Done when. Reprocessing the same data yields identical product keys, and the share of 
fallback matches is reported. 
F064 — Base period and weekday-matched base prices 
What it is. The reference against which all price changes are measured (index = 100). 
How it works. 
• 
Base period: the first full calendar month of data (configurable 
in methodology_version.base_period). 
• 
Base price P0(product, weekday) = mean total fare of that product for 
departures on that weekday during the base period, stored 
in base_price(product_key, dow, p0, n_obs, methodology_id, 
component). Weekday-matching removes the strong weekday effect, so a Sunday 
fare is compared with base Sundays. 
• 
Minimum evidence: at least 2 observations per (product, weekday). Otherwise 
use the cell's weekday factor times the product's all-weekday mean, 
flagged BASE_ESTIMATED. 
• 
During the base month itself the system runs in calibration: values are 
computed against the running base and labelled "Base period". This gives the 
demo a value from day one without a fake number. 
• 
Base prices are immutable once the base period closes; re-basing is a new 
methodology version. 
Done when. After the base period closes, the average relative across base-period data 
is 100.0 within tolerance, and re-computation never changes stored P0. 
F065 — Jevons elementary index 
What it is. The core price-change calculation inside each route × lead cell. 
How it works. 
• 
Relative: rel(i,t) = P(i,t) / P0(i, dow(i,t)). 
• 
Elementary index: I(r,l,t) = 100 × exp( (1/n) Σ ln rel(i,t) ), the 
geometric mean over matched products i. 
• 
Why geometric: the standard elementary formula for unweighted price 
relatives; it avoids the upward bias of the arithmetic mean of relatives and 
behaves well when consumers substitute between flights. 
• 
Computed in the log domain for numerical stability. Relatives are capped 
to [0.25, 4.0] and capped values flagged (a sanity guard, since a fourfold 
change in one product is nearly always a data problem). 
• 
Minimum sample: at least 5 matched products in a cell; otherwise the cell 
is INSUFFICIENT and excluded. 
• 
Optional variant: carrier-share weighted geometric mean 
using carrier_route_share (parameter). 
• 
Output stored 
in apix_cell_daily (geo_mean_relative, n_quotes, n_matched, mean_price
_inr, median_price_inr, coverage_ratio). 
Done when. The worked example from the locked architecture (route A 107.47, route 
B 105.00, APIx 106.48) passes to four decimals, and property tests (identical prices give 
100; scaling by k scales by k; row order irrelevant) pass. 
F066 — Lead-bucket aggregation 
What it is. Combines the seven lead-time cells into one route index. 
How it works. 
• 
I(r,t) = Σ_l λ_l × I(r,l,t) / Σ_l λ_l, over buckets present and 
not INSUFFICIENT. 
• 
Default λ: L01 0.08, L03 0.12, L07 0.20, L15 0.22, L30 0.22, L45 0.12, L60 0.04. 
These are assumptions about the booking curve, stored in lead_weight, 
shown openly on the Methodology page, and marked for calibration from 
booking-time distributions under a data-sharing agreement. 
• 
Rule: a route needs at least 4 of 7 buckets to produce an index; 
otherwise INSUFFICIENT_COVERAGE for that route/day. 
• 
Renormalisation over present buckets keeps the result meaningful when a bucket 
is missing, and the affected day is flagged. 
Done when. Missing-bucket scenarios in tests renormalise correctly, and fewer than 4 
buckets yields no route value. 
F067 — DGCA route weights 
What it is. Real traffic-based importance for each route. 
How it works. 
• 
Import: dgca_route_traffic.csv (columns origin, destination, period, 
passengers, source_doc, source_url). 
• 
w_r = passengers_r / Σ passengers over routes in the basket. Directional 
routes take the directional or split traffic as the data allows; the treatment is 
documented. 
• 
Validation: no negatives, no duplicates, weights sum to 1 (±1e-6), every basket 
route present. Missing routes stop the import. 
• 
Provenance: the source document, period and import time are stored 
on basket_version; the Methodology page shows them. 
• 
Annual refresh creates a new basket version (F073). 
• 
Illustrative mode: if real data is unavailable, --illustrative-weights seeds 
placeholders and the UI marks weights "Illustrative" everywhere they appear. 
Never present placeholders as official. 
Done when. A malformed file is rejected with a precise message, and a valid file 
produces a basket whose weights sum to 1. 
F068 — All-India APIx aggregation 
What it is. The single headline number, plus the series that break it down. 
How it works. 
• 
APIx(t) = Σ_r w_r × I(r,t) / Σ_r w_r, over routes that have a value. 
• 
Coverage rule: if routes with values represent less than 80% of total weight, the 
day is INSUFFICIENT_COVERAGE and the headline is not published. 
• 
Series keys produced (all with the same 
method): OVERALL, ROUTE:{code}, LEAD:{bucket}, CARRIER:{iata}, GROUP:{
route_group}, CHANNEL:{DIRECT|OTA}. 
• 
Carrier series use only that carrier's products, with route weights re-scaled to the 
routes it serves. 
• 
Each output row 
carries methodology_id, version, coverage_ratio and status (FLASH, OFFIC
IAL, REVISED). 
Done when. Overall equals the weighted average of route series in tests, and coverage 
below 80% suppresses publication. 
F069 — Coverage guard 
What it is. Prevents publishing a number built on too little data. 
How it works. 
• 
Levels: cell coverage (matched ÷ planned products), route coverage (buckets 
present), overall coverage (weight share of routes present). 
• 
Thresholds (configurable): cell below 60% excluded; route below 4 buckets 
excluded; overall below 80% blocks OFFICIAL and shows "Insufficient data". 
• 
Coverage between thresholds and 95% is published with a LOW_COVERAGE marker 
(hollow points, amber tile). 
• 
The number is displayed on the Coverage tile, each chart tooltip and the API 
(coverage_ratio). 
• 
Coverage heatmap (route × bucket) is on Data Health (F119). 
Done when. Simulated outages at each threshold trigger the exact behaviours listed. 
F070 — Incremental FLASH engine 
What it is. Updates the live index within seconds of each new quote without re-reading 
history. 
How it works. 
• 
State in Redis: cell 
hash cell:{obs_date}:{route}:{bucket} with sum_ln and n; product 
hash prod:{obs_date}:{product_key} with the latest ln_rel. 
• 
Update (atomic Lua script): for a new quote with ln_rel: if the product 
exists, sum_ln += ln_rel − old_ln_rel; otherwise sum_ln += ln_rel; n 
+= 1. Then recompute that cell's Jevons value (exp(sum_ln/n)), then the route 
index (from 7 cell values), then the overall (from 20 route values). Everything 
after the cell update is a small in-memory calculation. 
• 
Publish: an IndexTick (overall and the affected route) is emitted, throttled to at 
most 4 per second per series. 
• 
Persistence: every 30 seconds the engine writes provisional rows 
to apix_flash and apix_cell_daily (status='FLASH'). On restart it rebuilds 
the day's state from fare_quote_clean (a single scan of that day's rows). 
• 
FLASH price rule: the product's latest accepted quote of the day. 
• 
Correctness check: the OFFICIAL freeze (F071) recomputes the day from 
stored quotes and compares. 
Done when. After feeding a full simulated day, the incremental value equals the batch 
recomputation within 0.001 points, and a killed-and-restarted engine recovers the same 
state. 
F071 — OFFICIAL daily freeze 
What it is. The moment a day's number becomes final and publishable. 
How it works. 
1. Schedule: 23:30 IST daily (or manual trigger by APPROVER). 
2. Recompute the day from stored fare_quote_clean (not from Redis state): 
product daily price = mean of the day's accepted quotes; then cells, routes, 
overall. 
3. Checks: difference versus the last FLASH value within 0.05 points (otherwise 
logged as FLASH_OFFICIAL_DRIFT and investigated); coverage above thresholds; 
no unresolved critical data alert; quarantine backlog for the day below a limit. 
4. If checks pass, 
write apix_cell_daily and apix_series_daily with status='OFFICIAL', pu
blished_at, and emit index.official.published (webhooks F113, 
notifications F035, report triggers F105). 
5. If checks fail, the day stays FLASH, an alert is raised, and an approver can override 
with a written reason (F095). 
6. Late data: quotes arriving after cut-off belong to the next day's observations. 
Corrections to a frozen day go through revisions only. 
7. Idempotent: running the freeze twice yields the same result and no duplicate 
rows. 
Done when. The freeze on a seeded day reproduces stored values exactly, failing 
checks block publication, and reruns are safe. 
F072 — Weekly and monthly rollups 
What it is. Aggregated views of the daily official series. 
How it works. 
• 
Database views apix_weekly (ISO weeks, Monday start) 
and apix_monthly (calendar months) average the daily OFFICIAL values and 
record the minimum coverage inside the period. 
• 
Both are refreshed after every official freeze. 
• 
In-progress periods are computed on the fly, labelled "n of m days". 
• 
The API also returns the period-end value alongside the average, since some 
users prefer it. 
• 
Rollups never re-weight; they only average published values, so they always 
reconcile with the daily series. 
Done when. Independent recomputation from daily rows matches rollups exactly on 
the seeded data. 
F073 — Chain-linking and weight updates 
What it is. Lets weights change (for example each year) without breaking the series. 
How it works. 
• 
When a new basket becomes active on month start T, the new series is linked to 
the old one: APIx_new(t) = APIx_old(T−1) × [ Σ w'_r I'(r,t) / Σ w'_r 
I'(r,T−1) ] for t ≥ T, where I' uses base prices re-referenced to the link 
month. 
• 
A chain_link(link_id, effective_from, old_basket, new_basket, 
link_factor, computed_at) table stores each link. 
• 
Historical published values are not restated; the series shows a 
"Methodology/weights change" marker (F022). 
• 
Invariants tested: continuity at T−1 to T (no artificial jump beyond the true price 
movement), and monotonic consistency when weights are identical. 
Done when. Activating a basket with identical weights produces no change in the 
series; activating one with different weights produces continuity at the link. 
F074 — Overlap splicing of new products 
What it is. New flights enter the index without creating a fake jump. 
How it works. 
• 
When a product first appears with no base price for its weekday, P0_new = 
P_first_observation / (I_cell(t_first) / 100), so its first relative 
equals the cell's current index level, contributing neutrally. 
• 
The product is flagged SPLICED for its first 28 days. 
• 
Cap: if spliced products exceed 30% of a cell's matched set, the cell is 
flagged HIGH_SPLICE_SHARE (the index there leans on assumptions). 
• 
Retiring products simply drop out; no imputation. 
Done when. Injecting 50 new products on one day in tests moves the cell index by less 
than 0.05 points. 
F075 — Alternate bases (total, base fare, fuel, taxes) 
What it is. The same index, computed for each fare component so analysts see what 
drove a change. 
How it works. 
• 
Bases: TOTAL, BASE, FUEL, TAXES. Each has its own base prices 
(base_price.component) and its own relatives; the code path is identical. 
• 
Contribution decomposition: the change in the total is approximately Σ_k 
s_k × ΔI_k, where s_k is component k's share of total price in the base period. 
Shown as a stacked contribution bar on the Explorer. 
• 
Component series require the component split (not ESTIMATED_SPLIT); coverage 
per component is reported. 
Done when. Component contributions sum to the total change within a stated 
tolerance in tests.

F087 — Real-time WebSocket ticks 
What it is. Pushes live numbers to the browser. 
How it works. 
• 
Connect: POST /api/v1/auth/ws-ticket returns a single-use 30-second 
ticket; the client opens wss://…/api/v1/stream?ticket=…. The server 
validates origin, ticket and session. 
• 
Subscribe: messages {"op":"subscribe","channels":[…]}; each channel is 
authorised by permission. 
• 
Server: subscribes to Redis Pub/Sub, conflates to at most one message per 
channel per 250 ms (keeping the latest), and keeps a bounded per-connection 
queue of 100 messages (drop-oldest, with a SLOW_CONSUMER notice). 
• 
Client: a useLiveSeries hook patches the TanStack Query cache so charts 
append points and tiles update without refetching. Messages are ordered 
by event_id and duplicates ignored. 
• 
Efficiency: one shared socket per browser (leader tab via BroadcastChannel) 
rather than one per tab. 
• 
Limits: 10 connections per user, 50 channels per connection, 4 KB max message. 
Done when. 500 concurrent simulated clients receive ticks with p95 delivery under 1 
second, and slow clients don't affect others. 
F088 — Reconnect and resume 
What it is. No missed updates after a network drop. 
How it works. 
• 
Every event has an event_id (a Redis Stream ID). The server keeps the last 
~10,000 events per series in apix:stream:{series}. 
• 
On reconnect the client sends resume_from per channel; the server replays 
newer events and acknowledges with replay_count. 
• 
If the gap is older than retention, the server 
sends {"op":"resync_required"} and the client refetches via REST and then 
resumes. 
• 
Backoff 1, 2, 4, 8, 16, 30 s with jitter; browser online/offline events shortcut 
waiting (F016). 
Done when. Dropping the connection for 60 seconds during a simulated stream yields 
a chart identical to one that never disconnected.

A. Trust, Provenance and Governance 
F091 — Provenance Drawer 
What it is. Click any number or chart point and a side drawer shows exactly how it was 
made. This is the "Prove" layer of the interface. 
How it works. 
• 
Opens from KPI tiles, chart points, table cells and report figures. Endpoint: GET 
/api/v1/index/provenance/{series_key}/{date}. 
• 
Header: value, date, status pill (Provisional, Official, Revised), methodology 
version, basket version, coverage, code version, "computed at" time. 
• 
Contribution table: each route with its weight, route index, contribution in 
points, and number of matched products. A toggle switches to lead-bucket 
contributions. 
• 
Quality summary: share of quotes rejected, flagged and imputed; number of 
low-coverage cells; share of spliced products. 
• 
Sample quotes: ten representative quotes (highest-contribution first), each 
linking to the Quote Inspector (F093). 
• 
Inputs digest: a SHA-256 over the sorted list of (product_key, daily 
price) pairs used, stored in index_run.input_digest. Two computations with 
the same digest must give the same value. 
• 
Actions: Reproduce (F092), Export evidence (JSON or PDF), Copy citation. The 
citation text reads: APIx OVERALL, 21 Sep 2026 = 117.79 (methodology 
M1.0, basket BASKET-2026-A, version 1, retrieved 22 Sep 2026 
08:50 IST). 
• 
Permissions: users with series:read see the summary and contributions; 
only those with prices:read see quote-level rows. 
Data / API. New table index_run(run_id, obs_date, methodology_id, 
basket_id, code_version, input_digest, status, computed_at). One row is 
written per freeze and per revision. 
Edge cases. For FLASH points the drawer shows the current provisional state and says 
so. Dates older than the raw retention window still show summaries (which are kept 
forever) but note that quote samples may be unavailable. 
Done when. Every published point resolves to a drawer, contributions sum to the 
value (within rounding), and the citation text is correct. 
F092 — Reproduce this number 
What it is. A button that recomputes a published value from stored data and proves it 
matches. 
How it works. 
1. POST /api/v1/index/provenance/{series}/{date}/reproduce starts the 
check (synchronous for one date, asynchronous for ranges). 
2. The engine runs the same code path as production in read-only replay mode 
(F102): loads the stored clean quotes for that day, the base prices, the 
methodology version and basket recorded in index_run, and recomputes cells, 
routes and overall. 
3. Compares each level (cell, route, overall) with the stored values, tolerance 1e-6. 
4. Result: a green tick "Reproduced exactly" with the digest and timing, or a diff 
table showing which cells differ and by how much. 
5. Outcome is stored in reproduction_check(check_id, run_id, ok, 
max_abs_diff, checked_by, checked_at, code_version). 
• 
Determinism rules: prices held as exact decimals; logs computed in float64 
with a fixed summation order (sorted by product key); stable sorting; no 
dependence on wall-clock time or random state. 
• 
If the code version has changed since the run, the check uses the current code 
and states this. A mismatch is then classified as either "code change" or "data 
changed since" (for example, a later revision). 
Edge cases. Revised days reproduce against the latest version by default, with a 
selector to reproduce an earlier vintage. 
Done when. Reproducing 100 random seeded days yields exact matches, and 
deliberately corrupting a stored quote produces a failing check with a precise diff. 
F093 — Quote Inspector with lineage 
What it is. A detailed view of one fare observation and everything that happened to it. 
How it works. A modal opened from any quote row, containing: 
• 
Facts: flight, carrier, route, departure, lead days and bucket, fare family, source 
and channel, seats left, data origin. 
• 
Fare breakdown bar: base, fuel, taxes, fee, total, with an "estimated split" 
marker if applicable. 
• 
Rule decisions: a list of R01 to R12, each showing Pass, Flag or Reject with the 
parameters used. 
• 
Outlier context: its robust z-score plotted against the histogram of the cell's 
trailing 14-day distribution. 
• 
Index effect: this quote's ln(relative) and how much it moved its cell (in 
points), so users can see that one quote rarely matters. 
• 
Raw payload viewer: the captured JSON, rendered as text nodes only (never 
HTML), collapsible, capped at 200 KB with a "download full" link, sensitive fields 
redacted. Viewing a raw payload writes an audit event. 
• 
Lineage graph: task, capture (hash), raw row, clean row, cell, route, overall, 
each a clickable node with its row ID. 
Edge cases. Simulated quotes show "Generated by simulator" in place of a payload. 
Rejected quotes (from quarantine) show why they were rejected and who reviewed 
them. 
Done when. Any quote in the table opens with a complete lineage, and the payload 
viewer never executes or renders markup from the payload. 
F094 — Revision system 
What it is. Controlled correction of published numbers, with full history. Published 
values are never silently overwritten. 
How it works. 
• 
Triggers: accepting quarantined data (F060), late data, a parser fix, a weight 
update, a methodology change, a discovered error. 
• 
Process: an authorised user opens "Revise" on an affected day (modal M6). The 
system recomputes the day (and any dependants such as weekly and monthly 
rollups), creates version n+1 with status REVISED, keeps version n intact, and 
writes an apix_revision row (old value, new value, reason code, note, 
approver). 
• 
Reason 
codes: LATE_DATA, PARSER_FIX, DQ_OVERRIDE, WEIGHT_UPDATE, METHOD_CHANG
E, ERROR_CORRECTION. 
• 
Revision policy (configurable, displayed on the Methodology page): routine 
revisions are allowed within 14 days of publication with one approver; older 
revisions require a senior approver and are labelled "Late revision". 
• 
Vintages: every API series endpoint accepts as_of=<timestamp> and returns 
the values as they were published at that time. This is the standard "real-
time database" practice in official statistics, letting users see how estimates 
evolved and reproduce past reports exactly. 
• 
Visibility: revised points show a dot on charts with old, new and reason on 
hover; the series table has a revision column; downstream reports show a 
revision note. 
• 
Notifications: subscribers receive index.revised events (F113) and an in-app 
notification. 
Done when. A revision creates a new version without altering the old, as_of returns 
the earlier value, and rollups update consistently. 
F095 — Publish and freeze workflow 
What it is. The controls around making a value official. 
How it works. 
• 
Automatic freeze at 23:30 IST (F071). 
• 
Manual freeze or override by an APPROVER: opens modal M7 showing the 
check results (coverage, FLASH-versus-recompute drift, open critical alerts, 
quarantine backlog). If a check fails, the approver can override with a mandatory 
written reason; overrides are marked on the published value ("Published with 
override"). 
• 
Hold state: a day can be placed on HOLD (for example while investigating), 
which blocks automatic publication and notifies approvers. A hold must be 
released or resolved within 24 hours or it escalates. 
• 
Publication calendar: a list of upcoming and past releases (daily values, 
weekly bulletins, monthly releases) with status. 
• 
Monthly release workflow: the monthly release moves through Draft (auto-
generated after the last daily freeze) to Review to Published, with the report 
(F106) attached. 
• 
Withdrawal is not offered: a wrong published value is corrected by a revision, 
preserving history. 
Done when. Overrides require reasons and are visible, holds block publication, and 
every action is audited. 
F096 — Methodology manager 
What it is. The screen where statisticians define and govern how the index is built. 
How it works. 
• 
Tabs: Overview (plain-language explanation and diagram of the five calculation 
steps), Basket and weights, Lead-time weights, Parameters, Versions and 
approvals. 
• 
Basket and weights: a table of routes with DGCA passengers, computed 
weights, an include toggle, carrier shares; a treemap of weights; import from CSV 
(F067) with validation. 
• 
Lead-time weights: sliders that keep the total at 100%, with numeric entry and 
a "reset to default" button. 
• 
Parameters: outlier thresholds, coverage minimums, imputation limit, channel 
policy, base period, fare-family basis, cap on relatives. 
• 
Editing model: the active version is read-only. "Create draft" clones it 
into DRAFT, which can be edited freely by METHODOLOGIST. All edits validate live 
(weights sum to 1, thresholds ordered correctly). 
• 
Draft changes never affect published numbers until approved and activated. 
Done when. A draft can be created, edited and validated, and cannot alter the active 
version. 
F097 — Change impact preview 
What it is. Shows what a proposed change would do to past numbers before anyone 
approves it. 
How it works. 
• 
POST /api/v1/methodology/{id}/impact-preview runs a shadow 
computation (via replay, F102) over the last 90 days (configurable) using the 
draft parameters, writing to an isolated sandbox schema. 
• 
Output: an overlay chart (active versus draft series), summary statistics (mean 
absolute difference in points, maximum difference and date, effect on YoY and 
MoM), route contribution changes, coverage changes, and a plain-language 
sentence ("This change would have raised APIx by 0.3 points on average, with a 
maximum of 0.9 on 12 Sep"). 
• 
Runs asynchronously with a progress bar (typically under 2 minutes at seeded 
scale), with a hard time limit and cancel button. 
• 
Results are stored in methodology_preview and attached to the approval 
request so approvers see them. 
Done when. A weight change produces a preview whose numbers match a manual 
recomputation, and nothing in production tables changes. 
F098 — Two-person approval workflow 
What it is. Nobody can change the official method alone. 
How it works. 
• 
States: DRAFT → IN_REVIEW → APPROVED → ACTIVE (with an effective date at a 
month boundary), or REJECTED / WITHDRAWN. 
• 
Rules: the author cannot approve their own change (409 
SELF_APPROVAL_FORBIDDEN); at least one APPROVER must approve; a required 
checklist (impact preview attached, documentation updated, effective date 
chosen) must be complete before submitting. 
• 
Approver actions: approve, request changes, or reject, each with a comment. 
Approval requires recent authentication (password or passkey re-entry within 
10 minutes). 
• 
Notifications to approvers on submission and to the author on decision. Stale 
drafts (30 days without activity) are flagged. 
• 
Activation at the effective date triggers chain-linking (F073) automatically and 
records the version as ACTIVE, superseding the previous one. 
• 
Every transition is written to the audit log. 
Done when. Self-approval is refused, unapproved changes cannot activate, and 
activation creates the chain link. 
F099 — Methodology versioning and diff 
What it is. Every method the platform ever used is preserved and comparable. 
How it works. 
• 
Versions are immutable and labelled M{major}.{minor}: a major change alters 
formulas, basket or structure; a minor change alters parameters. 
• 
Every published value stores its methodology_id. 
• 
Diff view: side-by-side comparison of any two versions: parameter table with 
changes highlighted, weights table with deltas, and impact statistics when a 
preview exists. 
• 
Changelog page: a readable history ("M1.1 (from 1 Jan 2027): weights updated 
to FY26 DGCA traffic. Effect on index: +0.2 points on average"). 
• 
Rollback: never edits history. It creates a new version identical to an earlier 
one, activated through the normal approval path. 
Done when. Any two versions can be diffed, and rollback produces a new version 
rather than mutating an old one. 
 
B. Validation 
F100 — Back-test Lab 
What it is. Proves the index tracks reality by comparing it against the official DGCA 
benchmark, as the problem statement requires. 
How it works. 
1. Configure: window (default last 30 days), methodology version, data origin, 
benchmark (DGCA_NATIONAL or a route). 
2. Run: POST /api/v1/validation/backtests (returns 202 and a run ID). The 
runner replays the window through the real pipeline using the Replay adapter 
into an isolated schema, so production data is untouched. 
3. Progress: a bar driven by the backtest.{run_id} channel through 
states QUEUED → REPLAYING → COMPUTING → COMPLETE. 
4. Results: overlay chart (APIx and DGCA, both rebased), metric cards (F103), a 
residual chart, and a table of the largest discrepancies with a notes field for 
hypotheses. 
• 
Honest comparison design: DGCA figures are monthly, so a 30-day window 
contains about one benchmark data point. The lab therefore offers two 
comparisons: (a) a daily overlay using linearly interpolated benchmark values 
(interpolated points shown hollow), for visual sanity only, and (b) a monthly 
comparison of APIx monthly averages with DGCA monthly averages, which 
becomes statistically meaningful once at least 6 months exist. A banner states 
this: "30 days gives one benchmark point. Use 6 months or more for statistical 
validation." 
• 
When the data origin is SIMULATED, a persistent banner says validation is 
illustrative. 
• 
Runs are saved; two runs can be compared side by side. 
Done when. A back-test completes end to end on the seeded data with metrics and 
overlay, and the banners appear in the right situations. 
F101 — DGCA benchmark uploader 
What it is. Brings official benchmark data into the platform safely. 
How it works. 
• 
Downloadable CSV template: period_month (YYYY-MM-01), route (blank 
for national), avg_fare_inr, source_doc, source_url. 
• 
Upload dialog validates before committing: file size under 5 MB, UTF-8, exact 
header match, month format, positive numeric fares, known route codes, 
duplicates. A preview table shows accepted and rejected rows with reasons; the 
user confirms to commit. 
• 
Existing periods are upserted as new versions (benchmark_dgca_fare keeps 
history), with the uploader and time recorded. 
• 
Parsing happens in a sandboxed worker; cells beginning with formula characters 
are rejected; the file is never opened by spreadsheet software on the server. 
• 
source_doc is mandatory, so every benchmark point is citable. 
Done when. A malformed file is rejected with row-level messages, and a valid file 
appears in the Validation Lab. 
F102 — Replay adapter and deterministic replay 
What it is. The ability to re-run history through the pipeline exactly, for back-tests, 
impact previews and reproduction. 
How it works. 
• 
The ReplayAdapter reads stored raw events (or stored captures for live data) in 
strict order (scraped_at, raw_id) and feeds them to the pipeline with 
a virtual clock, so time-dependent rules behave as they did originally. 
• 
All writes go to an isolated schema replay_{run_id} (tables created from 
templates), so production tables are never touched. Parameter overrides (draft 
methodology, rule thresholds) apply only inside the sandbox. 
• 
Same code, same rules: nothing in replay is special-cased. 
• 
The sandbox schema is dropped after a retention period (default 7 days) or on 
demand. 
• 
Speed: unthrottled (the seeded 60-day dataset replays in a few minutes on the 
demo VM). 
Done when. Replaying a day without overrides reproduces stored outputs exactly, and 
production tables show zero writes during replay (asserted by a test).

F110 — API keys and scopes 
What it is. Safe, controllable machine access. 
How it works. 
• 
Creation: Developers page, "Create key": name, scopes 
(series:read, prices:read, analytics:read, reports:read, stream:subscr
ibe, ingest:write), optional IP allow-list (CIDR), expiry (default 1 year, 
maximum 2). 
• 
Format: apx_live_<8-char prefix>_<32 random bytes base32>. Sandbox 
keys start with apx_test_. The distinctive prefix helps automated secret 
scanners detect leaks. 
• 
Storage: only the prefix and an Argon2id hash of the secret. The full secret is 
displayed once, with a copy button and a warning. 
• 
Verification: look up by prefix, constant-time hash comparison, then check 
scopes, IP allow-list, expiry and revocation. 
• 
Rotation: creates a new key while the old remains valid for a chosen overlap 
(default 7 days). 
• 
Management: list with last-used time, last IP, usage; revoke immediately. Keys 
can never be used for admin functions. 
• 
Every creation, rotation and revocation is audited and notified to the owner. 
Done when. Revoked keys fail within 5 seconds, and the database contains no 
recoverable secrets.

F113 — Signed webhooks 
What it is. The platform notifies external systems when things happen. 
How it works. 
• 
Events: index.official.published, index.revised, anomaly.created, ale
rt.created, report.completed, source.circuit_opened, source.circuit_
closed. 
• 
Registration: URL (HTTPS only; validated against SSRF: DNS resolution,

response; Replay re-sends a delivery; Test sends a sample event.

Receivers are advised to verify the signature, reject timestamps older than 5 
minutes, and de-duplicate by delivery ID (delivery order is not guaranteed). 
• 
Secret rotation supports a 24-hour dual-secret overlap. 
Done when. A receiver verifying the signature accepts genuine deliveries and rejects 
tampered ones, and SSRF attempts to internal addresses are refused.

F118 — Drift detector and circuit breaker 
What it is. Notices when a source changes or breaks, and protects the index from bad

F122 — Statistical anomaly detection (STL residual) 
What it is. Automatically spots unusual price movements, accounting for normal 
weekly patterns. 
How it works. 
• 
Model: STL decomposition (weekly period 7, robust fitting) on the daily series of 
each scope (overall, each route, each carrier). The residual is scaled by its robust 
spread: score = |residual| / (1.4826 × MAD(residuals)). 
• 
Thresholds: 3.5 to 4.5 is INFO, 4.5 to 6 is WARN, above 6 is CRITICAL. 
• 
Cadence: evaluated after each cycle and at the daily freeze; intraday cell-level 
checks compare each cell with its value at the same point of previous cycles. 
• 
Cold start: needs at least 14 days (two weekly periods); before that the feature is 
disabled and the page says "Anomaly detection starts after 14 days of data". 
• 
Output: anomaly_event rows with scope, detector, severity, score, expected and 
observed values, and an explanation (F124). Duplicate events for the same scope 
and day are merged. 
• 
Evaluation: on simulated data with injected events, the harness reports recall 
and false alarms, and the Alerts page shows the detector's own track record 
("Confirmed 9 of 12 events reviewed"). 
Done when. Injected spikes of at least 8% are detected with recall of at least 0.9, and 
normal weekend cycles do not trigger. 
F123 — Cross-carrier agreement classifier 
What it is. Tells whether an unusual move is a genuine market-wide change or a data 
problem. 
How it works. For each anomalous cell, in the same time window (2 hours or the same 
cycle): 
• 
Carrier agreement = share of carriers with at least 3 matched products whose 
price moved beyond a threshold in the same direction. 
• 
Classification: MARKET_MOVE if at least 60% agree; CARRIER_SPECIFIC if one 
carrier moved alone (a fare action); SOURCE_SPECIFIC if the move appears in 
only one source or channel (a likely data problem); DATA_SUSPECT if a single 
quote is responsible. 
• 
The class is stored with the anomaly and used by the cleaner (F058) to 
downgrade rejects to flags for market moves, and by the explanation generator 
(F124). 
Done when. Scenarios covering each class produce the right label in tests. 
F124 — Explanation and attribution generator 
What it is. Turns an anomaly into a sentence and a breakdown a person can 
understand and act on. 
How it works. 
• 
Inputs: the anomaly, expected versus observed (from the STL fit), top 
contributors by route and lead bucket (the same contribution maths as F085), 
carrier agreement class, coinciding events (festival calendar F047, surcharge 
change F140, fare-cap events F141), coverage. 
• 
Output 
JSON: summary, expected, observed, magnitude_pct, top_contributors, car

F125 — Booking savings simulator 
What it is. An interactive tool showing what booking earlier could save, backed by 
observed data. 
How it works. 
•

with"), chosen by sliders from 1 to 60 days, plus preset chips (last-minute versus 
2 weeks, 2 weeks versus 1 month). 
•

P(l_early) / P(l_late). The rupee estimate multiplies by the route's median 
fare at the later lead. 
• 
Shows the result as a sentence ("Booking 15 days ahead instead of 3 saves about 
26%, roughly ₹1,400 on a typical DEL–BOM fare"), with a range from the fit's 
confidence band. 
•

guarantee for any specific flight." On simulated data, the origin badge and a note

Done when. Sliders update results instantly using cached curve parameters, and

F126 — Elasticity fitting and time evolution 
What it is. The statistics behind the elasticity chart and the savings simulator. 
How it works. 
• 
Model: P(l) = a + b·exp(−l/τ) fitted by robust non-linear least squares 
(SciPy least_squares with soft-L1 loss) to quote-level relative prices across 
lead days (not only the seven bucket means, since seven points cannot support a 
stable three-parameter fit). 
• 
Constraints: a > 0, b > 0, τ between 2 and 40 days; sensible starting values 
(a from the longest-lead price, b from the shortest, τ = 9). 
• 
Fallback: if the fit fails or R² is below 0.6, use monotone interpolation of log-
price by lead bucket and label the result "Approximate". 
• 
Uncertainty: 200 bootstrap resamples give 90% intervals for τ and the last-
minute premium. 
• 
Schedule: nightly per scope (all-India and each route with sufficient data, at 
least 300 quotes in the window), plus on demand. 
• 
Time evolution: weekly fits over rolling 30-day windows, stored 
in elasticity_curve, show how the curve steepens before festivals. A change of 
more than 20% week-on-week in the premium raises an informational alert. 
Done when. On simulated data with a known τ, the fit recovers it within 15%, and 
failed fits fall back cleanly.

F135 — Multi-factor authentication 
What it is. A second proof of identity beyond the password. 
How it works. 
•

•

regeneration invalidates old ones. 
•

policy, with a grace period of 7 days for new requirements. 
•

enrol. 
• 
Deliberately not offered: SMS one-time codes, because of SIM-swap and 
interception risk. 
• 
Step-up: sensitive actions (approve, publish, create key, change roles) request a 
fresh factor within the last 10 minutes. 
Done when. Enrolment, login, backup-code use, replay rejection and step-up all work

A. Forecasting and Forward-Looking Signals 
F136 — Nowcast and forecast with intervals 
What it is. A projection of where APIx is heading, including an estimate of the current 
month before it finishes. It answers the problem statement's point that CPI "lags behind 
true airfare inflation". 
How it works. 
• 
Target: the log of the daily OFFICIAL OVERALL series (log so changes are 
proportional). 
• 
Model: SARIMAX from statsmodels, with exogenous inputs: festival and holiday 
bump profiles from the event calendar (F047), and the forward booking-curve 
indicator (F137). Because the index is already weekday-matched, weekly 
seasonality is small, but it is tested and kept only if it improves out-of-sample 
error. 
• 
Horizon: 1 to 30 days ahead. Monthly nowcast = observed days so far plus 
forecast days remaining, averaged as the monthly rollup would be. 
• 
Intervals: 80% and 95% prediction intervals from simulated model paths 
(1,000 draws). 
• 
Honesty gate: every night a rolling-origin evaluation (expanding window, 
1-day and 7-day horizons) computes MAPE and actual interval coverage, and 
compares against a naive baseline (tomorrow equals today). If the model does 
not beat the baseline, the UI labels the forecast "Not better than a simple 
baseline" and shows the baseline instead. 
• 
Data requirement: at least 60 days of history for SARIMAX; between 30 and 
60 days, a damped-trend ETS model is used; below 30 days the feature is off with 
an explanatory message. 
• 
Schedule and storage: retrained nightly after the freeze; rows 
in forecast(run_id, made_at, target_date, horizon, point, lo80, 
hi80, lo95, hi95, model, params). 
• 
Display: a shaded band on the trend chart (F019) labelled "Forecast, not 
official", a card "Expected October average: 121 to 125 (80% range)", and the 
evaluation record shown in a tooltip. Forecasts never appear in official reports as 
facts; if included, they sit in a clearly labelled section. 
• 
Endpoint: GET /api/v1/index/nowcast?horizon_days=30. 
Edge cases. After a methodology change (chain link), the model refits on the linked 
series. During an active hold or insufficient coverage, no new forecast is published. 
Done when. On simulated data with known dynamics, interval coverage is within 10 
percentage points of nominal (an 80% interval contains about 70–90% of outcomes), 
and the baseline gate works. 
F137 — Forward booking-curve indicator 
What it is. A look at what fares for future travel dates are today, a genuinely forward-
looking signal unavailable to a manual survey. 
How it works. 
• 
The platform observes prices today for departures up to 60 days ahead. 
Comparing prices across departure dates, after removing the normal effect of 
booking lead time, shows which upcoming weeks are priced high. 
• 
Lead adjustment: each observed price is divided by the fitted lead curve value 
at its lead (P(l) from F126) to express it as a "15-day-equivalent" price, so a fare 
observed 45 days out is comparable with one observed 7 days out. 
• 
Forward index by departure week: the weighted matched-product mean of 
lead-adjusted relatives for departures in that week, computed with the same 
route weights. Stored in forward_index(obs_date, dep_week_start, 
value, n_products, coverage). 
• 
Display: "What travellers will pay in the coming weeks, as priced today", a chart 
over the next 8 weeks, with weeks that sit more than 5% above the current week 
highlighted, and their overlap with festival events noted. 
• 
Use: feeds the nowcast as an exogenous input. 
• 
Caveat shown: airlines release inventory and adjust fares as departure 
approaches, so this is an early signal, not a promise. 
Done when. On simulated data with a festival in week 5, the forward index shows the 
bump in that week, and lead adjustment removes the artificial slope that raw prices 
would show. 
F138 — Multivariate anomaly detection (Isolation Forest) 
What it is. A second detector that finds unusual combinations the single-series 
detector misses. Optional and always corroborating. 
How it works. 
• 
Features per cell and cycle: relative price change, change in seats left, carrier 
agreement share, lead bucket, hour of collection, route weight, and recent 
volatility. 
• 
Model: scikit-learn IsolationForest, contamination 0.5%, trained weekly on 
the trailing 28 days, fixed random seed. 
• 
Output: an anomaly score; events created only at INFO severity unless 
corroborated by the STL detector (F122) or the carrier agreement classifier 
(F123), in which case severity escalates. 
• 
Explanation: the two features with the largest robust z-scores are named in 
plain words ("unusually large seat drop with a small price change"). 
• 
Guardrail: it never rejects or alters data. It only creates review items. 
• 
Detector performance is tracked from resolved reviews. 
Done when. On simulated data with injected multi-signal events, the detector flags 
them, and it never modifies a quote. 
F139 — Regime-shift detection (CUSUM) 
What it is. Detects sustained level shifts, such as a fare war or a persistent surcharge 
increase, that single-day detectors miss. 
How it works. 
• 
Method: two-sided CUSUM on the standardised STL residuals: S⁺_t = max(0, 
S⁺_{t−1} + z_t − k) and S⁻_t = min(0, S⁻_{t−1} + z_t + k) with k = 
0.5 and alarm threshold h = 5 (in standard-deviation units), configurable. 
• 
On alarm: record an event with the estimated change date (the last time the 
statistic was zero), direction and size (the mean residual since then), then reset. 
• 
Interpretation: combines with carrier agreement (F123) and the surcharge 
detector (F140) to label likely 
nature: MARKET_WIDE_SHIFT, CARRIER_PRICING_SHIFT, SURCHARGE_STEP. 
• 
Runs per scope (overall, route, carrier) after each freeze. 
• 
Parameters and average run length trade-offs are documented on the 
Methodology page, since sensitivity choices shape false alarms. 
Done when. A simulated persistent +6% shift is detected within about 4 days with the 
change date estimated within 2 days, and stationary noise yields at most one false alarm 
per 200 days. 
F140 — Fuel-surcharge change detector 
What it is. Distinguishes airline price moves from fuel cost pass-through, using the 
fare decomposition. 
How it works. 
• 
Tracks the ratio fuel_surcharge / base_fare per carrier and route. 
• 
Step detection: the 3-day median compared with the previous 7-day median; 
an event fires when the ratio changes by more than 15% (relative) while the base 
fare changes by less than 3%. 
• 
Cross-carrier check: when several carriers step together, the event is 
labelled SURCHARGE_INDUSTRY_WIDE. 
• 
Effects: adds an entry to the event calendar (FUEL_PRICE, source "detected") 
shown as a chart marker, feeds the anomaly explanation (F124), and is 
highlighted in the component chart (F084). 
• 
Manual entries are also supported for known fuel-price revision dates (often 
monthly, verify current practice), so analysts can add context the data can't 
reveal. 
Done when. A simulated surcharge step is detected with the right date and labelled 
correctly, and a base-fare change alone does not trigger it. 
F141 — Fare-cap and regulatory event detector 
What it is. Notices when a price ceiling seems to be in effect, since caps distort the 
index and analysts need to know. 
How it works. 
• 
Signature heuristics on a route: the maximum observed fare is nearly 
identical across carriers, the share of quotes within 1% of that maximum jumps 
above 20%, and fare dispersion in high-demand buckets collapses (variance falls 
more than 50% versus the previous 14 days). 
• 
Output: an anomaly_event of type POSSIBLE_FARE_CAP with route, the 
apparent ceiling in ₹, number of carriers and confidence. Wording is hedged 
("consistent with a fare ceiling"). 
• 
Confirmation: an analyst can confirm and link the official notice, which adds 
a REGULATORY event to the calendar with the source reference. Detection alone is 
never presented as fact. 
• 
Effect on the index: none automatically (a capped price is still the price paid). 
The explanation generator and charts annotate the period. 
Done when. A simulated cap on one route triggers detection, and unrelated high-
demand periods do not. 
 
B. Collection Intelligence 
F142 — AI-assisted adapter repair (human-gated) 
What it is. When a source's page or API changes and breaks parsing, the system drafts 
a fix for an engineer to review. It never deploys changes on its own. 
How it works. 
1. Trigger: the drift detector (F118) opens a circuit with evidence. 
2. Context assembly: the previous golden payload and its expected parse, a 
sample of the new failing payload, the current parser module, and the failing test 
output. All payload content is wrapped and labelled as untrusted data, size-
limited, and stripped of anything resembling credentials. No production data, 
secrets or network access are included. 
3. Proposal: a language model (provider configurable) returns a patch limited to 
the adapter's parser file. 
4. Automated checks in a sandbox: the diff may touch only allowed paths; 
static analysis rejects new network, file-system, subprocess or eval use; the patch 
must pass all golden tests and produce the expected fields on the new sample. 
5. Change request: a pull request opens with the diff, test results, a plain-
language explanation and a confidence note. 
6. Human approval: an engineer reviews and merges through the normal CI and 
deployment path. Only then does the half-open probe (F118) test the fixed 
adapter. 
• 
Prompt-injection defence: because scraped pages are hostile inputs, the 
model has no tools and no ability to act; its only output is a text diff that goes 
through the checks above and human review. 
• 
Controls: feature flag, per-day cost cap, kill switch, audit log of every proposal, 
and metrics (proposal pass rate, time from drift to fix). 
• 
In the 48-hour build: presented as a scripted demo using one recorded, real 
example. Live automation is a production feature. 
Done when. On a fixture with a deliberately changed payload, the pipeline produces a 
patch that passes the sandbox checks and opens a pull request, and a patch touching a 
forbidden path is rejected automatically. 
F143 — Source health scoring and automatic fallback routing 
What it is. A numeric health score per source and a rule-based way to keep coverage 
up when one fails. 
How it works. 
• 
Score (0–100): 40% success rate, 20% parse rate, 20% (inverse) block rate, 
10% latency versus baseline, 10% data freshness, computed over the last 20 tasks 
and per source-route cell. 
• 
Fallback ladder for a cell whose primary source is unhealthy: (1) another 
airline-direct or OTA source that sells the same route, (2) a licensed feed if 
configured, (3) carry-forward within limits (F059), (4) exclude and renormalise. 
• 
Comparability rules: substituted quotes are flagged FALLBACK_SOURCE; the 
channel policy (F062) still applies; if fallback-sourced products exceed 25% of a 
cell's matched set, the cell is flagged so users know the number leans on a 
substitute. 
• 
Reversion: when the primary recovers (circuit closed and score above 80 for 
three cycles), routing reverts automatically. 
• 
Every decision is recorded in fallback_decision(cycle_id, route_id, 
bucket_id, primary_source, fallback_source, reason, 
decided_at) and shown on the Coverage matrix and Data Health page. 
Done when. Taking a source offline in tests triggers the correct ladder step, the 
fallback share cap flags as specified, and the system reverts after recovery. 
 
C. Integrity, Governance and Security 
F144 — Tamper-evident hash-chained audit log 
What it is. An audit trail where any alteration or deletion of history is detectable. 
How it works. 
• 
Chain: each row stores prev_hash and row_hash = SHA-256(prev_hash ‖ 
canonical_json(row)). Canonical JSON means sorted keys, UTF-8, no 
whitespace, fixed timestamp format. 
• 
Concurrency: one chain per organisation plus a platform chain; inserts take a 
transaction-level advisory lock on the chain ID so the order is well-defined. 
Budget: 500 events per second per organisation, with batching for bulk actions. 
• 
Database enforcement: triggers block UPDATE and DELETE; application roles 
have no such privileges (F146 and Part D role definitions). 
• 
Anchoring: each night the final hash of each chain is written to an object-lock 
(write-once) bucket and, in production, timestamped with an external RFC 3161 
time-stamp authority. This makes tampering detectable even by someone with 
database superuser access. 
• 
Verification: a job recomputes the chain nightly and on demand (the Verify 
chain button, F131), reporting the first mismatch or gap. A failure raises a 
critical alert. 
• 
Backup awareness: restores are followed by a verification run and a recorded 
note. 
Done when. Altering a row directly in the database causes verification to fail at that 
row, and deleting a row is detected as a gap. 
F145 — Large-move hold-and-review publication gate 
What it is. An extra safeguard: unusually big moves are reviewed by a person before 
becoming official. 
How it works. 
• 
At the freeze (F071), if the day-over-day APIx change exceeds 3% or 4 standard 
deviations of the historical daily changes (whichever is larger), or any route 
moves more than 10%, the day is placed on HOLD instead of publishing. 
• 
The approver sees: the change, the attribution (F085), the anomaly explanation 
(F124), coverage, spliced-product share, source health, and quarantine status, on 
one review screen. 
• 
Actions: Publish with note ("Reviewed large move: festival 
demand"), Investigate (keeps the hold and assigns a task), Revise data (via 
quarantine review, then re-freeze). 
• 
Holds expire into an escalation after 24 hours. Publishing after review annotates 
the point permanently on charts. 
• 
Thresholds are configurable; the false-hold rate is tracked so the gate does not 
become noise. 
Done when. A simulated 5% jump is held, the review screen shows all inputs, and 
publishing records the reviewer and note. 
F146 — Multi-tenant isolation (row-level security) 
What it is. Several organisations can share one platform without ever seeing each 
other's private data. Production feature; the H build has a single tenant but the hooks 
exist. 
How it works. 
• 
Data classes: (1) Platform-level shared data: reference tables, cleaned market 
data and the official APIx series. (2) Tenant-owned data: saved views, alert 
rules, reports, webhooks, API keys, notes, custom baskets and indexes, users, 
audit entries. Every tenant-owned table has org_id. 
• 
Enforcement in layers: 
1. The API sets SET LOCAL app.org_id = '<org from verified 
token>' at the start of every request. 
2. PostgreSQL row-level security policies on tenant-owned tables restrict 
rows to org_id = current_setting('app.org_id'). Application roles 
do not have BYPASSRLS. 
3. Redis keys and cache entries include the org ID; WebSocket channels are 
namespaced by org. 
4. Object storage prefixes are per organisation with IAM policies; per-tenant 
encryption keys. 
• 
Automated isolation tests: with two tenants' fixtures, a generated test suite 
(from the OpenAPI file) attempts every endpoint with tenant A credentials 
against tenant B's object IDs and expects 404 or 403. It runs on every merge. 
• 
Fairness: per-tenant rate limits and query timeouts to prevent noisy 
neighbours. 
• 
Offboarding: export of tenant data, then verified deletion of tenant-owned rows 
and keys, with a certificate of deletion. 
Done when. The isolation suite passes with zero cross-tenant reads or writes, and a 
query issued without the org context returns no tenant rows. 
F147 — Custom baskets per tenant 
What it is. Organisations define their own route mix and weights, for example an 
airline's network, a bank's travel-linked exposure or a corporate travel programme. 
Production feature. 
How it works. 
• 
A tenant creates up to 10 baskets of up to 100 routes each, with weights entered 
or imported from CSV (validated like F067). 
• 
Efficient computation: cell-level indices are shared (platform-level), so a 
tenant basket only recomputes the route and aggregate levels, which is cheap and 
fast. 
• 
Output series are named TENANT:{org}:{basket} and appear only for that 
tenant, in the Explorer, API and reports. 
• 
Only weights and route selection are customisable. Cleaning rules and index 
formulas are not, so tenant series stay comparable and trustworthy. 
• 
Optional internal approval workflow for basket changes within the tenant; every 
change versioned. 
• 
Usage feeds billing hooks (number of baskets and routes). 
Done when. A tenant basket reproduces the platform index when given the platform 
weights, and tenant B cannot see tenant A's basket. 
F148 — Custom index builder 
What it is. A no-code tool to build a weighted composite index from existing series. 
Production feature. 
How it works. 
• 
Builder UI: pick component series (routes, carriers, lead buckets, channels, 
route groups, up to 20), assign weights (sliders that sum to 100%), choose the 
method (weighted arithmetic of index levels, chain-linked; or weighted 
geometric), choose a base date (rebased to 100), and preview against OVERALL. 
• 
Example: a "Business travel index" of 60% metro routes at lead L03–L07 plus 
40% carrier-specific series. 
• 
Computation: daily and incremental from stored series values, saved 
in custom_index(index_id, org_id, name, definition, method, 
base_date, ...), and available through API and reports. 
• 
Integrity guardrails: custom indices are always labelled "Custom index, not 
official APIx", cannot use the name or branding "APIx", carry a permanent badge, 
and their exports include their definition. Sharing stays inside the tenant unless 
approved. 
Done when. A composite with a single 100% component equals that series exactly, and 
labels appear on every view and export. 
 
D. Intelligent Assistance 
F149 — Grounded "Ask AeroIndex" assistant 
What it is. Ask a question in plain language and get an answer with a chart and 
citations. Optional, off by default, and built so it cannot make up numbers. 
How it works. 
• 
Scope: questions about the platform's data ("Why did airfares rise this week?", 
"Which route is most expensive to book last minute?", "How has Delhi–Mumbai 
changed since August?"). 
• 
Tool-only design: the model does not query the database. It can call a fixed set 
of read-only 
tools: get_series, get_contributions, get_elasticity, get_anomalies, ge
t_coverage, get_route_summary. Tools run with the asker's own 
permissions (the same API and row-level security), so the assistant can never 
show more than the user could. 
• 
Answer format: a short answer, a chart built from tool data, and citations: 
each number links to the Provenance Drawer (F091). A "How I got this" panel 
lists the tool calls made. 
• 
Number guard: after generation, every numeric value in the text must appear 
in a tool result (within rounding). Otherwise the answer is regenerated or the 
unsupported figure is removed. The assistant is instructed to say "the data 
doesn't show that" rather than speculate. 
• 
Injection safety: tools return only numbers, dates and enumerated labels, 
never free text taken from scraped pages, so hostile web content can't reach the 
model. 
• 
Controls: per-user rate limits and cost budgets, full logging of questions and 
tool calls (audited), organisation-level enable switch, model hosting in line with 
the data-residency policy, and an evaluation set of 100 questions with expected 
tool plans, run in CI. 
• 
Never used to write official reports. 
Done when. On the evaluation set, at least 95% of answers contain only tool-supported 
numbers, and cross-tenant or unauthorised requests return refusals. 
F150 — Scenario and what-if simulator 
What it is. A sandbox for asking "what if?" with transparent assumptions, for example 
a fuel surcharge rise or a demand surge. 
How it works. 
• 
Shocks the user can set: fuel-surcharge change (percent), tax or fee change, 
festival-style demand increase for chosen dates and routes, capacity reduction on 
a route (modelled as a demand-pressure shift). 
• 
Calculation (deliberately simple and explained): 
o Component shocks pass through by share: ΔAPIx ≈ Σ_k s_k × shock_k 
× pass-through_k, with base-period shares s_k (F075) and adjustable 
pass-through (default 1.0 for surcharge and taxes). 
o Demand shocks reuse the average historical bump profile estimated 
from past events in the calendar (amplitude and width), scaled by the 
user's factor. 
• 
Output: projected APIx path against the baseline forecast (F136) with a range, 
and a table of assumptions. 
• 
Labels: "Illustrative scenario, not a forecast", with the assumptions listed and 
each editable. 
• 
Scenarios are saved (scenario table), shareable inside the organisation, and 
comparable side by side. 
Done when. A zero shock reproduces the baseline, and a known surcharge change 
yields the hand-calculated effect. 
F151 — CPI bridge (indicative contribution) 
What it is. Translates the airfare index movement into an indicative contribution to 
the CPI transport component. Optional and clearly caveated. 
How it works. 
• 
The user (or an administrator) supplies parameters that belong to the 
statistics office: the weight of airfares within the relevant CPI group and the 
weight of that group in the all-items CPI, each with a source note and effective 
date. The platform never hard-codes them, because the official weights are 
MoSPI's to define. 
• 
Calculation: contribution_to_CPI_change (percentage points) = 
w_group × w_air_in_group × (monthly APIx change %), shown at monthly 
frequency to match CPI. 
• 
Outputs an "indicative contribution" in basis points with the assumption list. 
• 
Always labelled "Indicative, not a CPI forecast". Parameter changes are 
versioned and audited. 
Done when. With the parameters set to known values, the output matches a hand 
calculation, and the label is present on every view and export.

Powers incident response and revision decisions.

F154 — Partner ingest gateway 
What it is. A secure door for approved partners to send fare data. Production feature. 
How it works. 
• 
Interfaces: REST POST /api/v1/ingest/quotes (batches up to 5,000 quotes) 
and gRPC client-streaming for high volume. 
• 
Authentication: per-partner credentials with HMAC-signed batches

• 
Idempotency: batch_id ensures re-sent batches don't double count.

• 
Operations: per-partner quotas, delivery SLA dashboards (timeliness, rejection 
rate), dead-letter queue, and audit of every batch. 
Done when. A tampered batch (bad signature) is rejected, a replayed batch is ignored,

F156 — Load-adaptive autoscaling (production) 
What it is. The platform grows and shrinks with demand automatically. 
How it works. 
• 
Kubernetes with: KEDA scaling scraper workers on queue depth; HPA scaling

Guardrails: minimum and maximum replicas per service, cost alarms, and

F157 — Disaster recovery and point-in-time restore (production) 
What it is. A tested ability to recover from data loss or a regional failure. 
How it works. 
• 
Targets: recovery point objective 15 minutes, recovery time objective 1 hour for 
the database. 
• 
Mechanisms: continuous WAL archiving for point-in-time recovery, daily base

versioning and replication; infrastructure defined as code for rebuild.

Redis: treated as disposable; recovery rebuilds live state from the database

• 
Drills: a monthly automated restore into an isolated environment, followed by

and reproduce checks on random published days (F092). Results are

• 
Runbooks: replica promotion, cross-region failover, communication templates

F158 — Access-pattern security monitoring (production) 
What it is. Detecting suspicious use of the platform, whether from stolen credentials,

How it works.

• 
Honeytokens: decoy API keys (apx_live_canary…) and decoy records placed

• 
Integration: structured events forwarded to a SIEM; dashboards for the 
security team. 
Done when (P). Simulated attacks (pagination sweep, credential stuffing, canary key

4. Change control after the lock 
• 
Feature IDs F001–F160 are permanent. Nothing is renumbered. 
• 
Adding, removing or re-prioritising a feature requires a short written entry 
(ADR) stating what changes, why, and the effect on the 48-hour plan. 
• 
A feature marked Must can be moved down only if its thin slice is unachievable; 
the decision is recorded the same hour. 
• 
After hour 46 nothing new is merged.
